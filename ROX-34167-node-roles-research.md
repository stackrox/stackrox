# Research: Compliance Operator node-role auto-discovery on non-OpenShift clusters

Context: PR [stackrox/stackrox#23344](https://github.com/stackrox/stackrox/pull/23344) (`gualvare/rox-34167-sensor-autodiscover-roles`, worktree `/tmp/opencode/rox-34167-sensor`). Code under review: `sensor/kubernetes/complianceoperator/noderoles.go`, `noderoles_test.go`, `utils.go`, `handler_impl.go`, `pkg/env/compliance_operator.go`.

## 1. Does Compliance Operator support non-OpenShift Kubernetes?

Yes, with caveats.

- The repo's own README calls it "a OpenShift Operator" (`README.md:5` in the vendored `github.com/ComplianceAsCode/compliance-operator@v1.8.2`), but `doc/install.md:3-8` says the install guide covers "an OpenShift or Kubernetes cluster" and gives a Helm-based install path independent of OLM/OpenShift.
- The shipped Helm chart (`config/helm/values.yaml`) has a `platform` value with documented options `'openshift', 'eks', 'generic', and 'unknown'`, and ships an EKS-specific override file, `config/helm/eks-values.yaml`.
- `values.yaml` explicitly documents the OpenShift-centric default doesn't apply elsewhere:
  > "By default, the compliance-operator will deploy to nodes tagged with the master kubernetes role, which is present in OpenShift deployments. You may need to omit this option to run the compliance-operator on other platforms, like EKS, where nodes do not have that role by default" (`config/helm/values.yaml:9-15`, also repeated for `tolerations:16-26`).
- `doc/usage.md:686-718` documents running CO on HyperShift hosted clusters (another non-standard-OpenShift-node topology).

So CO is designed to run on non-OpenShift Kubernetes (its own packaging anticipates EKS explicitly), but its defaults (operator scheduling, and by extension the node-role convention used for `ScanSetting.roles`) are OpenShift-shaped and the project's own docs call out that those defaults don't hold elsewhere.

## 2. Are `node-role.kubernetes.io/*` labels present by default on non-OpenShift nodes?

Short answer: control-plane labeling is common and often automatic; **worker-node role labeling is essentially never automatic** anywhere except OpenShift's own installer. This is a Kubernetes-wide, deliberate security restriction, not a quirk of one distro.

### The mechanism (applies everywhere)
- The kubelet is **not allowed to self-apply `node-role.kubernetes.io/*` labels** at node registration. This is enforced by the `NodeRestriction` admission controller for security reasons (a compromised/self-registering node must not be able to assert a privileged role). Kubernetes docs: [Creating a cluster with kubeadm — Managed node labels](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/) ("Because of the NodeRestriction admission controller, you cannot use the kubelet `--node-labels` flag to apply restricted labels (such as `node-role.kubernetes.io/*`) during initialization... To apply these labels manually, you must use `kubectl label` after the node has joined the cluster.")
- KEP-1143 ("Appropriate use of node-role labels") formalizes that `node-role.kubernetes.io/*` is reserved for end users/external tooling, not for in-tree Kubernetes behavior: https://www.kubernetes.dev/resources/keps/1143/
- Background/design discussion: https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/279-limit-node-access/README.md and https://github.com/kubernetes/kubernetes/issues/84912.

### Per-distro / per-provider findings

| Platform | Control-plane label | Worker label |
|---|---|---|
| **kubeadm (vanilla)** | `node-role.kubernetes.io/control-plane` applied automatically via `kubeadm init phase mark-control-plane`, using a *privileged* API client, not kubelet self-labeling (historically also `/master`, now deprecated/removed since ~1.24–1.25: [kubernetes/kubernetes#107533](https://github.com/kubernetes/kubernetes/pull/107533), [KEP 2067](https://github.com/kubernetes/enhancements/blob/master/keps/sig-cluster-lifecycle/kubeadm/2067-rename-master-label-taint/README.md)) | **Not set.** kubeadm has no `MarkWorker` phase; joining worker nodes get no `node-role.kubernetes.io/*` label by default. Confirmed by repeated upstream decisions to *not* add this: [kubernetes/kubeadm#1487](https://github.com/kubernetes/kubeadm/issues/1487) ("we decided to not do that... it's up to the cluster operators to do that"), [kubernetes/kubeadm#2509](https://github.com/kubernetes/kubeadm/issues/2509). `kubectl get nodes` shows `ROLES: <none>` for workers until an admin runs `kubectl label`. |
| **EKS** | n/a (managed control plane, not a Node object) | **Not set.** Attempting to pass `node-role.kubernetes.io/*` through EKS managed node group config can even *prevent the node from joining* ([aws/containers-roadmap#2465](https://github.com/aws/containers-roadmap/issues/2465)). Labeling is a documented post-join `kubectl label` step ([eksctl-io/eksctl#2363](https://github.com/eksctl-io/eksctl/issues/2363), [aws/containers-roadmap#1381](https://github.com/aws/containers-roadmap/issues/1381)). A `rancher/rke2` maintainer's informal survey states plainly: "EKS - none, GKE - none, AKS - 'agent'" ([rancher/rke2#505](https://github.com/rancher/rke2/issues/505)). |
| **GKE** | n/a (managed control plane) | **Not set.** "In GKE, nodes don't have any roles by default" — confirmed on [Stack Overflow](https://stackoverflow.com/questions/69310833/how-to-find-if-a-node-is-master-or-worker-in-k8s) citing GKE's own architecture docs, and by the rke2 survey above. |
| **AKS** | n/a (managed control plane) | **Not set** via the standard label; AKS reserves the `kubernetes.io/`/`kubernetes.azure.com/` prefixes and used `kubernetes.azure.com/role=agent` instead. `node-role.kubernetes.io/*` self-provisioning was historically blocked outright ([Azure/AKS#4628](https://github.com/Azure/AKS/issues/4628), [learn.microsoft.com/azure/aks/use-labels](https://learn.microsoft.com/en-us/azure/aks/use-labels)); AKS only recently added *opt-in* support for admins to set it manually post-join, still not automatic. |
| **k3s / RKE2** | `node-role.kubernetes.io/control-plane` (value `"true"`, deliberately non-standard vs. kubeadm's `""`) applied automatically to server nodes ([k3s-io/k3s#14046](https://github.com/k3s-io/k3s/issues/14046)). | **Not set for agent (worker) nodes.** `kubectl get nodes` shows `ROLES: <none>` for agents by default; k3s maintainers explicitly rejected auto-labeling agents as `worker` ([rancher/rke2#505](https://github.com/rancher/rke2/issues/505), multiple user reports e.g. [k3s-io/k3s#1289](https://github.com/k3s-io/k3s/issues/1289)). |
| **kind** | `node-role.kubernetes.io/control-plane` set on control-plane nodes. | **Not set** on worker nodes by default ([kubernetes-sigs/kind#3846](https://github.com/kubernetes-sigs/kind/issues/3846)). |

**Conclusion for §2**: control-plane nodes frequently get a `node-role.kubernetes.io/control-plane` (or distro-specific variant) label automatically, via a privileged path outside the kubelet. **No mainstream non-OpenShift distro or managed service labels worker nodes with `node-role.kubernetes.io/worker` (or any `node-role.kubernetes.io/*`) by default.** It is uniformly a manual/day-2 `kubectl label` step, or a custom controller, left to the administrator.

## 3. Does Sensor's hardcoded `[master, worker]` fallback match any nodes on a vanilla non-OCP cluster?

Given §2: on an unmodified kubeadm, EKS, GKE, AKS, k3s, or kind cluster, **no node carries `node-role.kubernetes.io/worker`**, and only kubeadm/k3s/kind label control-plane nodes with a role at all (and that role is `control-plane`, not `master`, on current versions — `master` has been removed from kubeadm's defaults since ~1.25, per [kubernetes/kubernetes#107533](https://github.com/kubernetes/kubernetes/pull/107533)). So `ScanSetting.roles: [master, worker]` on such a cluster compiles to two `NodeSelector`s (`{node-role.kubernetes.io/master: ""}`, `{node-role.kubernetes.io/worker: ""}`, built by CO's `utils.GetNodeRoleSelector`, `pkg/utils/nodeutils.go:220-227` in the vendored module) that **match zero nodes**, unless the administrator has manually labeled nodes to match that convention. Node-level compliance scans created under this default silently cover no nodes.

This is **not new or introduced by PR #23344**. It is the pre-existing behavior of Sensor's hardcoded roles (`utils.go:116,156` on `master`, unmodified — see current repo `sensor/kubernetes/complianceoperator/utils.go:116` and `:156`, both `Roles: []string{masterRole, workerRole}`), present since the code was first written, long before this PR.

## 4. Does PR #23344 regress or fail to fix this for non-OCP users?

**Does not regress, does not fix.** Concretely, from `sensor/kubernetes/complianceoperator/noderoles.go`:

- `machineConfigPoolGVR` (`noderoles.go:23-27`) is explicitly commented "These only exist on OpenShift."
- `discoverNodeRolesWithStatus` (`noderoles.go:81-107`):
  - returns the hardcoded `fallback := []string{masterRole, workerRole}` (`noderoles.go:82`) immediately if the feature env var `ROX_COMPLIANCE_AUTODISCOVER_NODE_ROLES` is off (default; `pkg/env/compliance_operator.go` new setting, default `false`),
  - and when the env var is on, falls back to the exact same hardcoded roles if the `machineconfigpools` list call errors (`noderoles.go:87-91`) — which is exactly what happens on a non-OpenShift cluster, confirmed by the unit test "falls back when MCP API is absent" (`noderoles_test.go:72-83`).
- The feature is additionally off by default (`ComplianceAutodiscoverNodeRoles = RegisterBooleanSetting("ROX_COMPLIANCE_AUTODISCOVER_NODE_ROLES", false)`), so for any cluster where the operator hasn't explicitly opted in, behavior is byte-identical to before this PR (confirmed by PR description: "when off, behavior is byte-identical to today").

So on non-OpenShift clusters, with or without this PR, with the feature on or off, the end state is identical: `[master, worker]`. This PR's value proposition is scoped to OpenShift clusters with custom `MachineConfigPool`s (e.g. `infra`), which previously were silently never scanned under the old hardcoded default; that gap is fixed only for OpenShift. **The non-OpenShift gap described in the task (default roles matching zero nodes) is a pre-existing issue in Sensor, unaddressed by this PR, and the PR does not make it worse.**

### A separate, already-in-flight mitigation exists
There is a sibling, independent PR already addressing *part* of this: [stackrox/stackrox#21825](https://github.com/stackrox/stackrox/pull/21825) ("make compliance scan node roles configurable", branch `gualvare/rox-34167-configurable-node-roles`, currently OPEN/DRAFT), gated by the already-merged feature flag `ComplianceCustomNodeRoles` (`pkg/features/list.go:42-43`, PR [#23274](https://github.com/stackrox/stackrox/pull/23274), MERGED). It adds a `node_roles` field all the way through the API/UI so an administrator can explicitly set, per scan config, any role list CO accepts — including `@all` (see §5) or custom strings matching labels they've applied by hand. This is a manual, admin-driven escape hatch, independent of and complementary to the MCP-based *default* computed by #23344. It does not auto-detect anything; the admin must still know (and apply) the right node labels, or use `@all`.

## 5. Evaluating the proposed Node-label-based fallback (union vs. true set-cover; unlabeled nodes)

### CO's own role→selector mapping (ground truth from vendored source)
From `pkg/utils/nodeutils.go` in `github.com/ComplianceAsCode/compliance-operator@v1.8.2` (same version this repo vendors, confirmed via `go.mod:18`):

```go
// nodeutils.go:220-227
func GetNodeRoleSelector(role string) map[string]string {
	if role == cmpv1alpha1.AllRoles {        // AllRoles = "@all"
		return map[string]string{}
	}
	return map[string]string{
		nodeRolePrefix + role: "",
	}
}
```

and the controller that uses it, `pkg/controller/scansettingbinding/scansettingbinding_controller.go:393-418` (`createScansWithSelector`): for a node-type scan, CO creates **one scan per role in `ScanSetting.Roles`**, each scan's `NodeSelector` set to `GetNodeRoleSelector(role)`. So:
- A normal role string `r` becomes selector `{node-role.kubernetes.io/<r>: ""}` — matches only nodes carrying that exact label key.
- `@all` becomes an **empty selector `{}`**, which the Kubernetes API/scheduler treats as "match everything" — every node is scanned, with no label requirement at all.
- `validateRoles` (`scansettingbinding_controller.go:372-391`) enforces `@all` can only appear alone (`len(Roles)==1 && Roles[0]=="@all"`), never combined with other roles — mixing is a validation error.
- Role strings are constrained to `^([a-zA-Z0-9-]){1,39}$` (`scansettingbinding_controller.go:41`).

CO also documents the remediation trade-off directly in the CRD comment (`pkg/apis/compliance/v1alpha1/scansetting_types.go:26-31`): `@all` runs on all nodes by skipping the node selector, but "the usage of `@all` in OpenShift is discouraged as the operator won't be able to apply remediations unless roles are specified" (remediation `MachineConfig`s are targeted per-`MachineConfigPool`/role; `@all` scans aren't tied to a pool, so there's nothing to attach a remediation `MachineConfig` to). This matches the rationale already recorded in PR #23344's own description for avoiding `@all` as the auto-discovery default on OpenShift.

CO's own node-role extraction helpers (`GetFirstNodeRole`, `GetNodeRoles`, `GetFirstNodeRoleLabel`, `nodeutils.go:44-100`) are a straightforward prefix-match over a label map — no set-cover logic of any kind exists in CO itself. These operate on an MCP's `nodeSelector`, not directly on `Node` objects; CO doesn't compute a minimal role set from actual Node labels anywhere in the source.

### Is union-of-present-labels sufficient, or is true minimal set-cover needed?
**Union is sufficient for coverage; set-cover minimization is a secondary quality-of-scans concern, not a correctness requirement.**

- Because each role becomes an *independent* scan with its own selector, roles are not mutually exclusive partitions — a node with both `node-role.kubernetes.io/master` and `node-role.kubernetes.io/control-plane` (a very common combination from kubeadm's own historical dual-labeling, and OpenShift's own masters which carry both `master` and `control-plane` in current OCP 4.9+) will simply be scanned twice, once under each role's per-role `ComplianceScan`. That's redundant *scan count*, not a coverage defect — every node that carries at least one `node-role.kubernetes.io/*` label is covered by taking the union of all such label keys observed across `Node` objects.
- True minimal set-cover (fewest roles whose selectors still union to "every labeled node") only matters if the operator cares about minimizing the number of scan objects/duplicate `ComplianceCheckResult`s for multiply-labeled nodes. That is a nice-to-have (less result noise, marginally fewer pods/resources), not something that changes which nodes get scanned. Implementing true set-cover (NP-hard in general, though trivial at the scale of node-role-label cardinality, which is typically < 10 distinct labels) adds algorithmic complexity for a benefit that's cosmetic, not functional. **Recommendation: use the simple union, not set-cover.**

### Nodes with zero `node-role.kubernetes.io/*` labels (the common EKS/GKE/AKS/kubeadm/k3s-worker case)
This is a hard limitation of Compliance Operator itself, not something Sensor can route around by querying more cluster state:
- There is **no selector value that matches "a node with no node-role label"** other than the empty selector, which is exactly what `@all` produces (and `@all` matches *every* node, labeled or not — it cannot be scoped to "only the unlabeled ones").
- Confirmed in source: `GetNodeRoleSelector` only has two cases — `@all` (empty selector, matches all nodes) or `<prefix>+role` (matches only nodes carrying that exact key). There is no third code path for "nodes lacking this label."
- Therefore: if Sensor discovers zero `node-role.kubernetes.io/*` labels anywhere in the cluster (the fully-unlabeled case — default EKS/GKE/AKS/kubeadm-workers-only/k3s-agents-only), the *only* way within CO's `roles` mechanism to scan any node at all is `@all`. There is no node-selector role string that will ever match an unlabeled node.

## 6. OpenShift MachineConfigPool node/pool membership semantics

From OpenShift's Machine Config Operator (MCO) docs and source/issue history:

- **A node can be in at most one MachineConfigPool.** "A node can be part of at most one pool" ([openshift/machine-config-operator docs/custom-pools.md](https://github.com/openshift/machine-config-operator/blob/master/docs/custom-pools.md)). Custom pools take priority over the default `worker` pool: "If a node has multiple labels that correspond to several MCPs, like `worker,infra`, it is managed by the infra custom pool, not the worker pool" ([OpenShift docs, Control plane architecture](https://cbippley.github.io/openshift-docs/OCPBUGS-4790/architecture/control-plane.html)). Crucially, removing the node from `worker`-pool *management* does not remove the `worker` **label** — by convention the node keeps `node-role.kubernetes.io/worker` *and* `node-role.kubernetes.io/infra` simultaneously unless the admin explicitly strips the `worker` label (`docs/custom-pools.md`: "if you want to use the node as a purely infra node, you can remove the worker pool... [by removing the worker label]"). This matters for the stackrox discovery code: since discovery reads each MCP's `nodeSelector`, not the node's actual labels, a node that's dual-labeled `worker,infra` surfaces as two separate discovered roles (`worker` from the `worker` MCP's selector, `infra` from the `infra` MCP's selector) regardless of which MCP "owns" it for MCO configuration purposes — this is fine for ACS's purposes since each role still produces a selector CO can use to find that node.
- **A node CAN belong to zero MCPs.** The MCO's own node controller comment states this is expected, not an error: `pkg/controller/node/node_controller.go` (quoted via the GH issue thread) — "This is not an error, as there might be nodes in cluster that are not managed by machineconfigpool." This can happen if a node's labels don't match any pool's `nodeSelector` at all.
- **A node CAN be ambiguous across multiple *custom* pools, which MCO treats as an error and excludes the node from all MCPs** until resolved: "node belongs to more than one MachineConfigPool, cannot proceed with this Node" ([openshift/machine-config-operator#571](https://github.com/openshift/machine-config-operator/issues/571), [openshift/machine-config-operator#429](https://github.com/openshift/machine-config-operator/issues/429), Red Hat KB [7080346](https://access.redhat.com/solutions/6970371)). This is specifically about two *custom* pools conflicting (e.g. both `infra` and `logging` custom pools matching the same node); master vs. worker is specially "subsumed" to avoid this (relevant for single-node/CodeReady-Containers topologies).
- **`master` and `worker` MCPs exist by default** on every OpenShift install, and the installer labels control-plane nodes `node-role.kubernetes.io/master`+`/control-plane` and compute nodes `node-role.kubernetes.io/worker` automatically (unlike vanilla kubeadm/EKS/GKE/AKS — this is OpenShift-installer-specific behavior, consistent with §2's "no node-role labeling is automatic in *Kubernetes core*" finding: OpenShift's installer is the privileged automation that applies these labels post-bootstrap, analogous to what kubeadm does only for control-plane nodes). The `worker` pool is *not* a literal "catch-all for anything unclaimed" in the MCO's matching logic (matching is still purely label-selector-based), but in practice, because the installer labels every non-master node `worker` and no other label by default, the `worker` pool functions as the catch-all for default installs; it stops being one only once an admin manually moves a node to a conflicting custom pool.
- **Our code's handling of zero-node pools is already correct and tested.** `discoverNodeRolesWithStatus` (`noderoles.go:93-99`) iterates every MCP in the list and extracts a role from `spec.nodeSelector.matchLabels` regardless of `status.machineCount`; it never looks at how many nodes currently match. This is confirmed directly by the test "zero-node pool still contributes its role" (`noderoles_test.go:100-104`), which constructs an MCP via `newMCP` with `status.machineCount` forced to `0` (`noderoles_test.go:37-38`) and asserts its role is still discovered. **"Pool has zero nodes" (already handled, by design) is a different scenario from "a node belongs to zero pools" (an MCO-level edge case, not something the MCP-nodeSelector-based discovery in this PR needs to special-case, since it never iterates nodes in the first place).**

## 7. Recommendation

1. **This PR (#23344) is safe to ship as-is for its stated scope (OpenShift custom-MachineConfigPool coverage).** It introduces no regression for non-OpenShift users: the fallback path is identical to pre-PR behavior, and the feature is off by default.
2. **The non-OpenShift "default roles match zero nodes" gap is real, pre-existing, and worth fixing separately**, but it's orthogonal to this PR's OpenShift-MCP mechanism. Two complementary angles already exist or are proposed:
   - **Already in flight:** PR #21825 + feature flag `ComplianceCustomNodeRoles` gives admins a manual override (`node_roles`, including `@all`) per scan config. This solves the problem *if the admin knows to use it*, but doesn't auto-detect anything.
   - **Proposed here:** a Node-label-based fallback, to try when MCP discovery is unavailable (`machineconfigpools` list fails, i.e. the existing `err != nil` branch in `discoverNodeRolesWithStatus`, `noderoles.go:87-91`) or returns nothing:
     - List `v1/nodes` (cluster-scoped `list`/`watch`, needs a new RBAC rule analogous to the `machineconfigpools` one added in `image/templates/helm/stackrox-secured-cluster/templates/sensor-compliance-rbac.yaml` — Sensor likely already has broad node read access elsewhere, worth checking before adding a new rule),
     - compute the **union** (not set-cover; see §5) of all `node-role.kubernetes.io/<x>` keys seen across all nodes, trimmed of the prefix, reusing the existing `nodeRolePrefix` constant and a loop structurally identical to `getFirstNodeRole`/`discoverNodeRolesWithStatus`'s existing `set.NewStringSet()` accumulation pattern (`noderoles.go:93-99`),
     - if that union is non-empty, return it (this is today's "discover roles from MCPs" behavior, generalized to read the label source of truth — Nodes — directly instead of via the OpenShift-only MCP indirection; it also naturally still works on OpenShift as an additional/alternate signal, independent of MCP existence),
     - if the union is empty (fully unlabeled cluster: default EKS/GKE/AKS/kubeadm/k3s), the only thing left within CO's `roles` model that can select *any* node is `@all` (§5) — so the last-resort fallback should become `["@all"]`, not `["master", "worker"]`, specifically for the case where **zero** `node-role.kubernetes.io/*` labels exist anywhere in the cluster. `["master","worker"]` has no advantage over `@all` when it's already established no node will match it; `@all` at least guarantees scan coverage, at the documented cost (CO doc comment, `scansetting_types.go:26-31`) of non-OpenShift remediation support being reduced — likely an acceptable trade since non-OpenShift CO remediation-via-`MachineConfig` isn't meaningful anyway (there's no MCO to apply `MachineConfig` remediations outside OpenShift in the first place).
     - Keep `["master","worker"]` as the fallback **only** for the "MCP list failed AND node list also failed/unavailable" double-failure case, to preserve current, tested, OpenShift-safe behavior when something is merely transiently broken rather than structurally absent.
   - This slots into `discoverNodeRolesWithStatus` as an additional branch after the existing `mcpList` error/empty-roles paths (`noderoles.go:87-104`), before falling back to the hardcoded default, and would need its own unit tests mirroring the existing MCP ones (env-off no-op, node-label union discovery, zero-labels-anywhere → `@all`, node-list failure → final `[master,worker]` fallback) plus a RBAC review for `nodes` `list`/`watch`.
3. Whichever fallback-of-last-resort is chosen, **surface it clearly in logs and in the PR/feature documentation** that `@all` has the documented remediation trade-off, so operators enabling auto-discovery on a non-OpenShift cluster understand why remediations might not apply the way they would on OpenShift.
