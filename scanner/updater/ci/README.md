# Scanner CI vulnerability bundle

The explicit Go fixtures in `generate/fixtures_*.go` describe packages and
advisories needed by CI scenarios. The generated ZIP stays in Git so unit and
importer tests work offline. Production serialization and matcher tests check
format compatibility when dependencies change; new scenarios require manual
fixture updates with an independent test expectation and source-data reference.

## Updating fixtures

Edit the fixtures and advance `defaultBundleRevision` beyond the ZIP's existing
member timestamps when the generated bytes change. From the repository root:

```sh
go generate ./scanner/updater/ci/generate
go run ./scanner/updater/ci/generate -check
go test ./scanner/updater/ci/generate ./scanner/updater/bundle
CI_MINIMAL_BUNDLE_PATH="$PWD/scanner/image/scanner/bundles/ci-minimal/vulnerabilities.zip" \
  go test ./scanner/updater -run '^TestCIMinimalBundle$'
go test ./scanner/matcher/updater/vuln -run '^TestCIMinimalBundleValid$'
```

The Scanner DB integration workflow also runs the fixture importer and matching
tests against disposable PostgreSQL databases. Locally, select a disposable
admin connection explicitly with `SCANNER_CI_TEST_DB` and run
`make -C scanner db-integration-test`. The tests create and drop databases.

## Publication

Commit the fixture changes and regenerated ZIP together. The Scanner updater
bundle workflow publishes only from `master`, on relevant pushes, its existing
schedule, or manual dispatch. It validates the committed ZIP and uploads it as:

```
https://definitions.stackrox.io/v4/vulnerability-bundles/ci-minimal-<sha256>/vulnerabilities.zip
```

The digest is calculated from the ZIP bytes. Existing objects are verified and
never overwritten. Publication verifies the public bytes, `Last-Modified`, and
conditional HTTP requests. The workflow summary contains the published URL.
The initial rollout publishes the bundle before a separate change enables CI
consumers. Generator tests alone do not establish full e2e coverage.
