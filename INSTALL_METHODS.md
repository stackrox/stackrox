# StackRox Installation Methods

This document describes how StackRox/ACS is installed on Kubernetes clusters,
aimed at AI agents and developers who need context on the installation landscape.

For developer deployment (local dev/test), see `deploy/AGENTS.md` and
`deploy/README.md` (roxie). This document covers the **production-facing
installation methods** and their evolution.

## Current state (as of 4.11)

The project is **consolidating from three installation methods down to one:
the operator.** The canonical statement is in `operator/install/README.md`:

> Due to significant maintenance burden of three installation methods, we are
> planning to consolidate on just one: the operator.

ROX-33099 is the umbrella JIRA ticket for the 4.11-scope consolidation work.

### The three methods

The codebase tracks installation method via `ManagerType` in
`proto/storage/cluster.proto`:

| Method | Proto enum | Telemetry label | Status |
|--------|-----------|----------------|--------|
| Manifest (roxctl generate) | `MANAGER_TYPE_MANUAL` | `"manifest"` | **Deprecated since 4.9** |
| Helm charts | `MANAGER_TYPE_HELM_CHART` | `"helm"` | **Deprecated since 4.11** |
| Operator | `MANAGER_TYPE_KUBERNETES_OPERATOR` | `"operator"` | **Active, recommended** |

Sensor detects the method at startup and maps it to a telemetry label via
`sensor/common/installmethod/install.go`. The env var `ROX_INSTALL_METHOD`
(`pkg/env/install.go`) carries the string value (`manifest`, `helm`, or
`rhacs-operator`).

### Installation method vs image flavor

These are two independent axes:

- **Installation method**: How you deploy (operator, Helm, manifest).
- **Image flavor**: What you deploy (`development_build`, `rhacs`, `opensource`).

Flavors are defined in `pkg/images/defaults/` and control image registries,
names, and chart branding. Any combination of method and flavor is possible,
though RHACS strongly favors the operator path.

## The operator

The operator (`operator/`) manages StackRox via two primary CRDs:

- `Central` (`platform.stackrox.io/v1alpha1`) -- Central services
- `SecuredCluster` (`platform.stackrox.io/v1alpha1`) -- Secured cluster services

A third CRD, `SecurityPolicy` (`config.stackrox.io/v1alpha1`), ships with the
bundle for config-as-code security policies.

### Helm charts as the rendering engine

The operator **embeds the same Helm charts** used by standalone Helm
installations. It translates CRD spec fields into Helm values, renders the
embedded chart templates, and applies the resulting resources. The chart
templates (in `image/templates/helm/`) are the single source of truth for all
Kubernetes resource definitions regardless of installation method.

Key code paths:
- `image/embed_charts.go` -- embeds charts via `//go:embed`, exposes
  `LoadChart()` and `LoadAndInstantiateChartTemplate()`
- `operator/internal/reconciler/` -- reconciliation pipeline
- `operator/pkg/values/translation/` -- CRD-to-Helm-values translation

### Installing the operator

On **OpenShift**: via OLM from the Red Hat Operator catalog. The operator
package name is `rhacs-operator` on the `stable` channel.

On **non-OpenShift Kubernetes**: via the **Operator Helm Chart**, a separate
chart that deploys the operator itself (not the operands):

```shell
helm repo add stackrox https://raw.githubusercontent.com/stackrox/helm-charts/main/opensource/
helm install --wait --namespace stackrox-operator-system --create-namespace \
  stackrox-operator stackrox/stackrox-operator
```

This chart is generated by `operator/hack/generate-chart.sh` and published
to `charts.stackrox.io` starting from 4.11.

### Migration from legacy methods

`roxctl` provides migration commands:

- `roxctl central migrate-to-operator` -- inspects a running deployment and
  generates a `Central` CR
- `roxctl sensor migrate-to-operator` -- generates a `SecuredCluster` CR

If applied in the same namespace as an existing legacy install, the operator
seamlessly takes over. See `operator/install/README.md` for details and
caveats -- the migration tooling is not yet aware of every customization
method.

The migration code lives in `pkg/migratetooperator/`.

## Helm charts (deprecated)

Two application Helm charts exist:
- `stackrox-central-services` -- deploys Central, Scanner, DB
- `stackrox-secured-cluster-services` -- deploys Sensor, Collector,
  Admission Controller

As of 4.11, using these charts directly is **deprecated** in favor of the
operator. The charts remain the rendering engine used internally by the
operator, but users should not install them standalone.

### Meta-templating system

Charts are not plain Helm charts. Files with `.htpl` suffix are processed
by a Go `text/template` pass (with `[<` `>]` delimiters to avoid conflicting
with Helm's `{{ }}`). This happens before standard Helm rendering.

Key concepts:
- `pkg/helm/charts/meta.go` -- `MetaValues` struct controlling instantiation
- `pkg/helm/template/chart_template.go` -- meta-template processing
- `image/templates/helm/shared/` -- templates shared between both charts
- Feature flags, image flavor, and render mode control chart output

Charts are instantiated in four contexts:
1. The operator (internal rendering)
2. `roxctl helm output` (deprecated CLI command)
3. Central's HTTP API (serves secured-cluster chart as ZIP)
4. Sensor bundle generation

### Chart flavors

Three flavors: `opensource` (quay.io/stackrox-io), `rhacs`
(registry.redhat.io), `development_build` (quay.io/rhacs-eng). Controlled by
`pkg/images/defaults/`.

### Chart publishing

Six artifacts per release (2 app charts x 2 flavors + operator chart x 2
flavors), published to:
- `charts.stackrox.io`
- `mirror.openshift.com/pub/rhacs/charts/`
- `github.com/stackrox/helm-charts` (opensource)

## Manifest installation (deprecated)

The original method: `roxctl central generate k8s/openshift` produces raw
YAML applied with `kubectl`. Deprecated since 4.9, with deprecation
strengthened in 4.11. All related roxctl commands carry
`DeprecatedInFavorOfOperator` (`roxctl/common/deprecation.go`).

## What is deprecated (4.11)

### roxctl commands
- `roxctl central generate {interactive,k8s,openshift}`
- `roxctl sensor generate {k8s,openshift}`
- `roxctl sensor get-bundle`
- `roxctl sensor generate-certs`
- `roxctl helm output {central-services,secured-cluster-services}`
- `roxctl helm derive-local-values`

### gRPC/REST endpoints
- gRPC: `GetCAConfig`, all `SensorUpgradeService` RPCs, `DeploymentFormat`
  enum, `PostCluster`, `PutCluster`
- REST: `/api/extensions/clusters/zip`,
  `/api/extensions/clusters/helm-config.yaml`,
  `/api/extensions/helm-charts/`

### UI
- Deprecation notices shown for Helm and manifest install paths (ROX-33125)

### Other
- PodSecurityPolicy support (ROX-35032)
- `app.k8s.io/v1beta1/Application` (ROX-35079)
- Plaintext endpoints via `ROX_PLAINTEXT_ENDPOINTS`

## Developer deployment (roxie)

For local development, **roxie** (`deploy/roxie/`,
https://github.com/stackrox/roxie) is the recommended tool. It **always
deploys via the operator** (creating `Central` and `SecuredCluster` CRs).
There is no option to deploy via Helm or manifests through roxie.

The legacy deploy scripts (`deploy/k8s/deploy-local.sh` etc.) are deprecated
in favor of roxie. See `deploy/README.md` for usage details.

## Historical timeline

| When | Event |
|------|-------|
| Pre-2019 | Docker Swarm + K8s manifests |
| Jan 2019 | Swarm removed (ROX-976) |
| 2019-2020 | `roxctl generate` is the primary method |
| 2020-2021 | Helm charts introduced, old charts removed |
| Apr 2021 | Operator scaffolding (ROX-6918), OpenShift-only |
| Jun 2022 | OSS Helm chart publishing (ROX-10079) |
| Oct 2025 | Manifest install deprecated (ROX-31191) |
| Mar 2026 | Operator enabled on non-OpenShift (ROX-33119); UI deprecation notices (ROX-33125) |
| Apr 2026 | migrate-to-operator CLI; roxie integration |
| May 2026 | All roxctl generate/helm commands deprecated (ROX-33179, ROX-33248) |
| Jul 2026 | Current state: operator is the only recommended method |
